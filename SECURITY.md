# Security Policy

## Reporting a vulnerability

Please **don't** open a public issue for a security problem.

Use GitHub's [private vulnerability
reporting](https://github.com/iridiumdesign/iridium-proto/security/advisories/new)
on this repository. If that isn't available to you, email
**brad@iridiumdesign.com**.

I maintain this crate on my own time, so I can't offer a same-day
response. I aim to acknowledge a report within a week and to have a fix
or a clear explanation within thirty days.

Please give me a reasonable window to ship a fix before publishing
details. I'll credit you in the advisory unless you'd rather I didn't.

## Supported versions

This crate is pre-1.0. Only the most recent release receives fixes —
there are no maintained back-branches.

## Scope

`proto` is a development tool. It connects to a database you name, reads
the catalogs, and writes files where you tell it to. It is not a runtime
dependency of anything it generates, and it holds no long-lived state.

Three things it handles are worth attacking.

**Credentials.** `proto` reads passwords from the config file, a file
that config names, an environment variable, `$PGPASSWORD`, and
`~/.pgpass`. None of them may reach an output file. Generated headers
name the *target* — `dev`, or the literal string `--url` — never a
connection string, because those headers get committed. A path by which
a password, a connection string, or the contents of a password file ends
up in generated output, in a log line, or in an error message is a
vulnerability. Report it.

**Paths.** Output file names are derived from schema and table names,
which are sanitized to alphanumerics and underscores before they reach a
path — a relation named `../../etc/passwd` becomes `______etc_passwd`.
An input that escapes the directory you passed to `--out-dir`,
`--mapper-dir`, or `--migrations-dir` is a vulnerability. So is one that
gets past the `@generated by proto` guard and overwrites a hand-written
file without `--force`.

**No `unsafe`.** The crate contains no `unsafe` blocks, so
memory-safety issues would have to come from a dependency rather than
from this code.

**Injection.** `tests/injection.rs` covers the three surfaces where a
name could stop being data: the queries a generated mapper runs (values
are bound, never interpolated, and nothing is assembled at run time),
the identifiers proto copies out of the catalogs into SQL text, and the
Rust string literal that SQL is embedded in. The round trip in
`scripts/smoke.sh` carries the same thing further: it creates a table
whose name is an injection payload, alongside a table for that payload
to destroy, generates and applies the functions, and fails if the
neighbour is gone. A finding in any of those is in scope.

## Out of scope

**The database you point it at is trusted.** `proto` reads identifiers,
comments, enum labels and default expressions out of the catalogs and
writes them into Rust and SQL that you then compile and run. It is a
transcription tool, and it assumes the schema is yours. Pointing it at a
database controlled by someone else and compiling the result is
equivalent to running their code, and no amount of escaping inside
`proto` changes that. If this matters to you, read what it emitted —
that is what stdout is for.

Within that, quoting is a robustness matter rather than a security one.
Identifiers are quoted where quoting changes the meaning — a reserved
word, a name Postgres would fold, a name carrying punctuation — and left
bare where it does not. If you find an identifier that still produces
SQL that will not parse, or one that escapes the string literal it is
written into, that is a bug and I want to know about it; please open a
normal public issue.

**Wrong output is a bug, not a vulnerability.** A Postgres type mapped
to the wrong Rust type, a nullable column emitted without `Option`, a
default that should have been left to the server, a mapper whose two
backends disagree — these are important and I want the report, they just
aren't security reports.

**What the generated code does is your code's problem.** Mappers are
parameterized: values are bound, never interpolated. If you find a
generated statement that interpolates a *value* rather than binding it,
that is in scope and is a real finding. But a generated mapper you have
since edited, or an application that passes untrusted input to a finder
it shouldn't, is outside what I can be responsible for.
